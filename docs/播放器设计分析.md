# 播放器连续播放设计分析

> 记录时间：早期讨论。状态：**多数建议已落地，但最终路线与本稿部分结论不同**。
>
> 目的：回答"主流播放器如何做到连续刷剧丝滑"、"滑动时空白处用图片填充是怎么回事"，
> 并给出针对短剧果果的性价比、流量、难度评估。
>
> ⚠️ 本文是**历史讨论稿**：当时建议「封面过渡 + LRU 缓存、不建议多播放器」，但最终
> 实施走的是「**本地流式 + 双播放器 + 预加载队列**」（见
> [`技术文档.md`](技术文档.md) §5.5~5.7），并因此牺牲了封面过渡。本文的价值在于
> 记录了「丝滑 = 预取 + 复用 + 缓存」的分析框架，具体取舍见
> [`产品设计文档.md`](产品设计文档.md)。

## 1. 当前架构（基线）

| 项 | 现状 |
|---|---|
| 播放方式 | 单集单 `VideoPlayerController`，切集时销毁重建 |
| 预取 | 播放中后台预下载 + 预解密**下一集**（已做） |
| 缓存 | 每集一个 `{vid}_{quality}_v3.mp4` 文件，**无 LRU 限额**，无限膨胀 |
| 切集交互 | 上滑/下滑 → 立即销毁当前 controller → 重新 `_load()` 下一集 |
| 清晰度 | 详情页选定（默认 720p），失败自动回退 720p |
| 封面 | 有 `series_cover` 元数据，但切集时**未做过渡视觉** |

关键量级（实测）：单集约 **720p ≈ 6MB（h264）**、**1080p ≈ 4MB（HEVC）**，
时长约 60~90s 的竖屏短剧。

## 2. "丝滑"的本质：预取 + 复用 + 缓存，三者缺一不可

主流短剧/短视频播放器（红果、抖音、快手）的连续播放靠三层：

1. **预取（prefetch）**：当前集播放时后台下载+解密下 1~3 集，切集时数据已就绪。
2. **播放器复用（playlist）**：一个播放器实例无缝衔接多集，避免反复 `initialize`
   （`initialize` 要等解复用、探测解码器、首帧，是切集卡顿的主要来源）。
3. **LRU 缓存**：最近看过的集留盘，切回不重新下载；有上限（如 1~2GB），
   超了就按"最久未用"淘汰，**不会无限保留**。

> 结论：只缓存不预取，切集仍需现下载；只预取不复用，切集仍有 `initialize` 等待。
> 三者叠加才有"丝滑"。

## 3. 滑动时"空白用图片填充"的真相

现象：滑动时能看到下一页跟着滑进来，空白处有一张图。

**那张图基本是"封面图"（元数据 `series_cover`），不是"视频首帧"。**

本质实现是 **PageView + 封面占位**：

- 每个"页面"= 一集，页面里先铺一张封面图（几十~200KB，几乎零流量）；
- 手指滑动时下一页封面跟着滑入（所以看起来"已经准备好了"）；
- 滑动落定后，才开始加载/播放这一集视频。

为什么不常用"首帧"：抽首帧要解码视频（贵），除非顺手截当前帧做缩略图；
而封面图是详情页本来就有的，直接复用，成本趋近于零。

## 4. 性价比 / 流量 / 难度评估（针对短剧果果）

| 功能 | 流量冲击 | 技术难度 | 性价比 | 建议 |
|---|---|---|---|---|
| 预取下一集（已做） | +1 集 ≈ 4~6MB | 低 | 高 | 保留 |
| 预取下 2~3 集 | 每集 +4~6MB | 低-中（要队列 + 播放时让带宽） | 中 | 可做，仅 WiFi |
| 切集封面过渡 | ~0（封面几 KB） | 中（播放页改 PageView 或加过渡层） | 高 | **值得做** |
| LRU 缓存限额 | 0（反而省磁盘） | 低 | 高 | **强烈建议** |
| 多播放器 PageView（真·抖音式） | 0 | **高** | 低 | 不建议 |
| 抽真实首帧 / 进度条雪碧图 | 0 | 中-高 | 低 | 不建议 |

### 4.1 两个"高难度低性价比"项为何不碰

**① 真·抖音式多播放器滑动**
需要同时维护 2~3 个 `VideoPlayerController`（= 2~3 个硬件解码器）：
- 内存与解码器并发数受限（本机 HEVC 硬解上限 16 路，但稳定同时跑 2~3 路已吃紧）；
- `video_player` 不支持播放列表复用，需换 `media_kit` 或自写平台通道；
- 收益只是"滑动时上一集还在播"的过渡动画。

对个人工具类 App 而言，这是为一点视觉花最重工程成本。当前"滑动→立即切集"已经够快，
缺的只是"封面跟着滑进来"这个便宜视觉。

**② 首帧图片 / 进度条雪碧图**
抽首帧需解码一帧，雪碧图要预生成所有关键帧，视觉收益小、成本高。

### 4.2 流量账（按 100 集 × 单集 5MB 粗算）

| 策略 | 单次看完一部的增量流量 | 说明 |
|---|---|---|
| 只播当前集 | 0 | 基线 |
| 预取下 1 集 | +5MB × 未看完的集 ≈ 最多 +5MB | 几乎可忽略 |
| 预取下 2 集 | 最多 +10MB | 可接受 |
| 预取下 3 集 | 最多 +15MB | 仅建议 WiFi |
| 封面过渡 | +几 KB | 可忽略 |
| LRU 限额 | 0（省磁盘，不省流量） | — |

## 5. 建议的实施优先级

1. **LRU 缓存限额**（如 1GB，超了删最旧）——零流量、省磁盘、零风险；
2. **切集封面过渡**（"封面先露出来、视频就绪再淡入"，替代"瞬间硬切"）——
   几乎零流量，丝滑感提升最大；
3. **预取下 2 集（仅 WiFi）**——中等收益、流量可控；
4. 多播放器 PageView、首帧/雪碧图——**不建议**。

## 6. 具体实施方案（供后续实施时参考）

### 6.1 LRU 缓存限额
- 扫描 `play_cache/` 目录下所有 `*.mp4`，记录 `size` 与 `mtime`；
- 总大小超过阈值（如 1GB）时，按 `mtime` 从旧到新删除，直到低于阈值；
- 触发时机：每次写入新缓存后、或 App 启动后台线程做一次；
- 不删除"正在播放/预取中"的文件（按文件名 `vid_quality_vX.mp4` 加锁或跳过）。

### 6.2 切集封面过渡
- 播放页在 `_load()` 加载期间，显示当前集的封面（`widget.drama.cover`）为底；
- 视频 `initialize` 完成、拿到首帧后，再淡入视频层（`AnimatedOpacity` / `AnimatedSwitcher`）；
- 上滑/下滑切集时，短暂显示目标集封面，再切入视频，视觉上"下一集已就绪"。

### 6.3 预取下 2 集（仅 WiFi）
- 维护一个预取队列，播放当前集时串行预取 `index+1`、`index+2`；
- 判断网络（`connectivity_plus` 或平台通道）仅 WiFi 时预取多集，移动网络只预取 1 集或不预取；
- 播放当前集时让出带宽（预取降速/暂停），避免和播放抢网。
